# KatanaDI Product Requirements Document

Статус: Draft v1  
Дата: 2026-03-15  
Проект: KatanaDI  
Платформа: macOS  
Тип продукта: internal utility / menu bar app

## 1. Product Summary

KatanaDI это минимальное macOS-приложение, которое маршрутизирует чистый DI-сигнал гитары из USB-аудиоустройства BOSS Katana Air в `Built-in Output` Mac без какой-либо обработки сигнала.

Продукт существует для одной задачи: дать предсказуемый, легковесный и постоянно доступный passthrough-канал между Katana Air и внешней цепью обработки через Axe-FX III, исключив из сигнального пути тяжёлый AU-хост и любые скрытые DSP-изменения.

## 2. Problem Statement

Текущий workaround использует Neural DSP Archetype Nolly X как промежуточный AU-хост для вывода DI-сигнала. Это создаёт несколько проблем:

- решение нестабильно для повседневной студийной работы;
- CPU- и RAM-стоимость неоправданно высока для задачи passthrough;
- поведение непрозрачно, так как нельзя гарантировать полное отсутствие обработки сигнала;
- цепь зависима от стороннего плагина, лицензии и его обновлений;
- при отключении или переподключении Katana работа требует лишних ручных действий.

Нужен специализированный utility-app, который делает одну вещь надёжно: берёт указанный входной канал одного CoreAudio-устройства и отправляет его в выбранный выход без DSP, эффектов и лишней логики.

## 3. Goals

### 3.1 Business / user goals

- Обеспечить постоянный и прозрачный DI passthrough для домашней студии.
- Упростить аудио-цепь и убрать зависимость от Neural DSP как транспортного слоя.
- Свести запуск к модели "включил Mac и Katana, всё заработало автоматически".

### 3.2 Product goals for v1

- Автоматически обнаруживать BOSS Katana Air и запускать routing без ручной настройки.
- Маршрутизировать DI-сигнал с выбранного входного канала в `Built-in Output`.
- Держать задержку на уровне, субъективно незаметном при игре.
- Переживать отключение и повторное подключение устройства без перезапуска приложения.
- Показывать понятный текущий статус системы в одном месте.

## 4. Non-Goals

Следующее не входит в MVP:

- аудиоэффекты, усилители, cabinet simulation, EQ или любая иная обработка сигнала;
- запись аудио в файл;
- routing между несколькими входами и несколькими выходами одновременно;
- встроенный микшер, meters, waveform UI или расширенный мониторинг;
- управление пресетами Katana;
- использование Aggregate Device как обязательной части решения;
- поддержка Windows или iOS;
- App Store distribution, notarization и коммерческая упаковка.

## 5. Target User and Context

### 5.1 Primary user

Один основной пользователь: музыкант/разработчик собственной студийной цепи, которому нужен надёжный DI routing без вмешательства в тон.

### 5.2 Environment

- Mac mini Late 2014
- Intel x86_64
- macOS 12.7.6 Monterey
- BOSS Katana Air как USB audio input
- `Built-in Output` Mac как физический выход
- пассивный DI-box
- Axe-FX III как downstream processor

### 5.3 Operating scenario

Пользователь включает Katana Air, подключает её по USB к Mac, запускает или автоматически поднимает KatanaDI и ожидает, что чистый сигнал гитары мгновенно оказывается на физическом выходе Mac без дополнительной настройки.

## 6. User Value Proposition

KatanaDI даёт:

- прозрачный passthrough вместо чёрного ящика;
- радикально более низкую нагрузку на систему;
- меньше точек отказа в студийной цепи;
- predictable startup и reconnect behavior;
- отдельный инструмент под конкретную задачу без побочных функций.

## 7. User Stories

### 7.1 Core stories

- Как пользователь, я хочу, чтобы приложение само находило Katana Air и начинало routing, чтобы не настраивать путь перед каждой игрой.
- Как пользователь, я хочу выбирать входной канал, чтобы при необходимости сменить DI-канал без пересборки приложения.
- Как пользователь, я хочу дублировать моно-сигнал в стерео или отправлять его только в один канал выхода, чтобы подстроиться под физическую коммутацию.
- Как пользователь, я хочу, чтобы приложение автоматически восстанавливалось после отключения Katana, чтобы не прерывать рабочий процесс.
- Как пользователь, я хочу видеть, работает ли passthrough прямо сейчас, чтобы быстро диагностировать проблемы.

### 7.2 Operational stories

- Как пользователь, я хочу, чтобы приложение сохраняло настройки между запусками.
- Как пользователь, я хочу запуск приложения при логине в систему.
- Как пользователь, я хочу, чтобы смена default output device в macOS не ломала routing, если целевой выход остаётся `Built-in Output`.

## 8. Scope

### 8.1 MVP scope

В релиз `v1` входят:

- menu bar app для macOS;
- автоматическое обнаружение Katana Air по имени или устойчивому совпадению имени;
- выбор входного канала;
- выбор режима вывода: `mono-left`, `mono-right`, `stereo`;
- автозапуск passthrough при наличии устройства;
- повторное подключение после disconnect/reconnect;
- сохранение настроек локально;
- индикация статуса;
- базовый лог ошибок и событий для диагностики.

### 8.2 Post-MVP candidates

- CLI-режим как отладочный инструмент;
- ручной выбор альтернативного output device;
- отображение sample rate и buffer size в расширенном статусе;
- горячая смена buffer size без полной перезагрузки приложения;
- экспорт диагностического лога;
- universal binary.

## 9. Functional Requirements

### FR-1 Device discovery

- Приложение должно обнаруживать доступные CoreAudio input/output devices при запуске.
- Приложение должно автоматически находить входное устройство, имя которого содержит `KATANA`, если конкретный UID ещё не сохранён.
- Приложение должно находить `Built-in Output` как целевой выход и привязываться к нему по имени или UID, а не к текущему system default device.

### FR-2 Automatic lifecycle

- Если Katana доступна при старте приложения, passthrough должен запускаться автоматически, если включён `autoStart`.
- Если Katana недоступна, приложение должно перейти в состояние ожидания и продолжать мониторинг устройств.
- При появлении Katana приложение должно автоматически перейти в активное состояние без ручного подтверждения.
- При исчезновении Katana приложение должно остановить routing, очистить активный pipeline и перейти в `waiting`.

### FR-3 Audio routing

- Приложение должно читать сигнал с одного выбранного входного канала Katana.
- Приложение должно выводить сигнал без аудиообработки, изменения уровня, суммирования или эффектов.
- Приложение должно поддерживать три режима назначения сигнала: `mono-left`, `mono-right`, `stereo`.
- В режиме `stereo` приложение должно дублировать моно-сигнал на оба выходных канала.
- Приложение должно корректно работать при sample rate, предоставленном входным устройством, если этот rate поддерживается выходом.
- Если текущий rate недоступен для целевого выхода, приложение должно попытаться применить заранее определённый fallback strategy и сообщить статус ошибки, если routing невозможен.

### FR-4 Settings

- Приложение должно хранить и восстанавливать между запусками следующие настройки: шаблон поиска input device, выбранный входной канал, режим output channels, buffer size, autoStart, start at login.
- Настройки должны быть доступны без редактирования кода.

### FR-5 Status and controls

- Приложение должно показывать текущий статус в menu bar.
- Приложение должно различать минимум три состояния: `active`, `waiting for device`, `error`.
- Из menu bar меню пользователь должен иметь доступ минимум к текущему статусу routing, выбору входного канала, выбору buffer size, выбору output mode, переключателю `Start at Login`, команде `Quit`.

### FR-6 Diagnostics

- Приложение должно логировать ключевые события: запуск приложения, обнаружение устройств, старт и остановка audio engine, ошибки инициализации, disconnect/reconnect событий.
- Логи должны быть достаточны, чтобы понять, почему passthrough не стартовал.

## 10. Non-Functional Requirements

### NFR-1 Signal integrity

- В аудиопути не должно быть намеренной DSP-обработки.
- Выходной сигнал должен быть функционально эквивалентен входному DI-сигналу с учётом неизбежного формата системного audio pipeline.
- Любые операции над буфером должны ограничиваться копированием канала в целевые выходные каналы.

### NFR-2 Latency

- Целевой baseline: buffer size 128 samples.
- Целевая воспринимаемая задержка: не ощущается как мешающая игре в реальном времени.
- Рабочий ориентир для v1: держать суммарную дополнительную задержку приложения минимальной и не добавлять ничего сверх системного I/O buffering.

### NFR-3 Performance

- CPU usage: ориентир менее 1% на целевой машине в steady state.
- Memory footprint: ориентир менее 20 MB.
- Приложение не должно требовать сторонних runtime/framework dependencies сверх системных библиотек.

### NFR-4 Reliability

- Приложение должно стабильно работать в долгих сессиях без деградации состояния.
- Повторное подключение Katana не должно требовать перезапуска приложения.
- Смена default audio device в системе не должна ломать routing, если `Built-in Output` остаётся доступен.

### NFR-5 Compatibility

- Минимальная поддерживаемая ОС: macOS 12.7.6.
- Основная целевая архитектура: Intel x86_64.
- Подпись и нотарификация не являются блокерами для v1.

## 11. UX Requirements

### 11.1 Interaction model

Основной интерфейс для v1: menu bar app. Это лучший компромисс между прозрачностью состояния и отсутствием лишнего UI.

### 11.2 Menu bar states

- `Active`: routing работает, пользователь видит зелёный статус и краткую сводку маршрута.
- `Waiting`: Katana недоступна, пользователь видит жёлтый статус и ожидание подключения.
- `Error`: routing не может быть запущен, пользователь видит красный статус и краткую причину.

### 11.3 Menu content

Минимальный состав меню:

- строка состояния вида `KATANA -> Built-in Output`;
- краткая строка параметров `Ch3, 48kHz, 128 samples`;
- selector входного канала;
- selector buffer size;
- selector output mode;
- toggle `Start at Login`;
- `Quit`.

### 11.4 UX principles

- Никаких окон, если это не требуется для системного permission/error case.
- Никаких визуальных элементов, не влияющих на routing.
- Все ключевые состояния должны быть понятны одним взглядом.

## 12. Technical Guardrails

Этот раздел фиксирует инженерные ограничения, важные для продукта:

- Использовать системные аудио API macOS и не строить решение поверх plugin hosts.
- Не включать в v1 внешние фреймворки ради UI, логирования или конфигурации.
- Архитектура должна позволять разделить device monitoring, audio engine и persistence на отдельные модули.
- Сигнальный путь должен быть реализован так, чтобы место потенциальной обработки было очевидно и легко проверялось ревью и тестами.

## 13. Dependencies and Assumptions

### Dependencies

- Наличие Katana Air, корректно определяемой macOS как USB audio device.
- Наличие встроенного аудиовыхода Mac.
- Реальная проверка на целевом железе.

### Assumptions

- Канал 3 Katana Air действительно содержит нужный DI-сигнал на текущем firmware.
- `Built-in Output` достаточно стабилен как фиксированная точка назначения.
- Для пользователя достаточно menu bar интерфейса без отдельного окна настроек.

## 14. Risks

### Product and technical risks

- У разных версий firmware Katana нужный DI-канал может отличаться.
- Часть sample rate combinations может требовать resampling или не запускаться напрямую.
- На старом Intel Mac возможны edge cases в CoreAudio lifecycle при частых reconnect.
- Поведение некоторых USB audio devices может отличаться после sleep/wake системы.

### Mitigations

- Делать номер входного канала настраиваемым.
- Валидировать sample rate и сообщать ошибку явно, а не работать молча некорректно.
- Добавить reconnect handling и явный reset audio engine.
- Проверить сценарии cold boot, unplug/replug и wake from sleep в тест-плане.

## 15. Success Metrics

Для `v1` продукт считается успешным, если:

- пользователь может включить Katana и получить DI-сигнал на `Built-in Output` без сторонних плагинов;
- приложение автоматически восстанавливает routing после переподключения устройства;
- при обычной игре нет субъективно мешающей задержки;
- системная нагрузка заметно ниже текущего workaround с Neural DSP;
- приложение можно использовать как постоянный элемент студийного сетапа, а не как временный hack.

## 16. Acceptance Criteria

- При подключённой Katana Air пользователь слышит чистый DI-сигнал на целевом тракте через `Built-in Output`.
- Выбранный входной канал действительно влияет на источник сигнала без необходимости менять код.
- Режимы `mono-left`, `mono-right` и `stereo` работают предсказуемо.
- При запуске приложения с доступной Katana routing стартует автоматически.
- При отключении Katana routing останавливается корректно, без зависания приложения.
- При повторном подключении Katana routing восстанавливается автоматически.
- При смене system default output routing не переключается на другой девайс, если `Built-in Output` доступен.
- В steady state приложение остаётся лёгким по CPU/RAM на целевой машине.

## 17. Release Plan

### Phase 1: Technical spike

- Подтвердить на реальном устройстве входной DI-канал.
- Подтвердить поддерживаемые sample rates Katana Air и `Built-in Output`.
- Проверить минимально жизнеспособный passthrough pipeline без UI.

### Phase 2: MVP implementation

- Реализовать device discovery, lifecycle handling и audio engine.
- Добавить menu bar UI и persistence.
- Добавить logging и recovery paths.

### Phase 3: Validation

- Протестировать cold start, reconnect, sleep/wake и долгую сессию.
- Сравнить субъективную задержку и загрузку CPU с текущим workaround.
- Провести end-to-end тест в полной студийной цепи `Katana -> Mac -> DI box -> Axe-FX`.

## 18. Open Questions

- Нужно ли в `v1` сразу поддерживать ручной выбор output device, или достаточно жёстко держаться за `Built-in Output`?
- Нужен ли CLI debug mode уже в первой версии для диагностики на старте?
- Где именно хранить настройки: в JSON-файле, `UserDefaults` или через более нативный app preferences слой?
- Требуется ли отдельная индикация ошибок sample rate mismatch вместо общего статуса `Error`?
- Нужен ли watchdog для сценариев sleep/wake, если базовый listener окажется недостаточно надёжным?

## 19. Appendix: Current Studio Signal Chain

```text
  -> monitors / recording
```
